大模型的上下文（Context）

概念学习资料 · 由 concept-learner 生成并人工核查

一、个人解释

上下文是模型在「这一次推理」中能看到的全部输入信息——系统提示、对话历史、工具返回的结果、检索到的文档片段等等。它决定了模型此刻「知道什么、被要求做什么」，是模型理解当前任务的全部依据。

打个比方：模型的参数像它「长期学到的知识」，而上下文像「摆在桌面上的当场材料」。桌子（上下文窗口）大小有限，材料放多了会放不下，也会更慢更贵。

二、核心机制 / 组成

  • Token 与分词器（Tokenizer）：文本先被切分成 token（词元），模型按 token 计费、计数，上下文长度也以 token 衡量。
  • 上下文窗口（Context Window）：一次能容纳的最大 token 数，超出部分会被截断或遗忘。
  • 注意力机制（Attention）：让模型在生成每个 token 时，关注上下文里最相关的部分，这是 Transformer 的核心（来源：《Attention Is All You Need》）。
  • 上下文的组成：系统提示（角色/规则）＋ 用户消息 ＋ 助手历史回复 ＋ 工具结果 ＋ 检索片段（RAG）都会被拼进上下文。
  • 检索增强生成（RAG）：当上下文窗口有限时，先检索相关文档再塞进上下文，让模型「现用现查」。

三、一个具体应用场景

场景：客服机器人回答关于「退货政策」的问题。

  1. 用户问：「我上个月买的耳机还能退吗？」
  2. 系统把「系统提示（你是客服助手）＋ 用户问题 ＋ 检索到的退货政策文档片段」一起放进上下文。
  3. 模型基于这段上下文判断：耳机属于 30 天无理由退货范围，用户已超期，于是给出「已超期，但可申请换货」的回复。

这里的关键是：模型本身不一定「背下」这家店的退货政策，是上下文里的检索片段让它此刻「知道」了规则。

四、容易混淆的问题 / 使用边界

容易混淆澄清
上下文长度 ≠ 模型「记忆力」上下文长不代表记得好。研究发现模型对中间位置的信息容易忽略（「Lost in the Middle」现象）。
上下文 ≠ 模型知识知识主要存在参数里，上下文是「当场输入」；两者会共同影响回答。
上下文窗口大 ≠ 一定更好塞得越多越贵、越慢，还可能引入噪音和错误。

使用边界

  • 超出窗口的信息会被截断，需要 RAG、摘要或压缩策略来兜底。
  • 上下文可被「提示注入」污染：外部内容可能诱导模型做出越界行为，需设防。
  • 成本与延迟随 token 数增长，长上下文并非免费的「更多记忆」。
